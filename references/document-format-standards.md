# 文档格式规范（Document Format Standards）

> **中央真相源 · 用户与专家团共建**。本文件定义**售前专家团**输出 Word/PDF 文档时必须遵守的格式标准（字体 / 字号 / 标题层级 / 颜色 / 边距 / 标题内容规范等）。docx-agent 渲染时须遵循本规范；build_docx.py / tencent-docx 编排器均消费此规范。
>
> **状态：现行生效**。本文件为中央真相源，由用户与专家团共建。**Word 文档输出以 §0.14「标准 Word 输出模板（样式模板.dotx）」为唯一准绳**（2026-10-14 用户定版，统一口径）；第〇节版式条目与"第一~第五轮答复"（2026-08-10）为历史记录，凡与 §0.14 冲突者，一律以 §0.14 为准。

> ⚠️ **2026-10-14 更新**：Word 文档输出**统一以 §0.14「标准 Word 输出模板」为准**（用户定版）——本节的**字体/字号/页边距/版式类条目转为历史存档**，与 §0.14 及配套规范 `word-template-style-spec.md` 冲突之处一律以后者为准；本节其余条目继续有效。

### 0.1 字体与字号总表

| 元素 | 字体 | 字号 | 字形 | 说明 |
|------|------|------|------|------|
| 封面·分类标签 | 黑体 | 小四 12pt | 常规 | 标题上方的类别行 |
| 封面·主标题 | 黑体 | 二号 22pt | 常规 | — |
| 封面·副标题 | 黑体 | 三号 16pt | 常规 | — |
| 封面·编制信息 | 宋体 | 五号 10.5pt | 常规 | 编制单位 / 日期 |
| 目录标题 | 黑体 | 三号 16pt | 常规 | — |
| 目录条目 | 宋体 | 小四 12pt | 常规 | 一级顶格、二级缩进 0.5cm |
| **部分标题**（第一部分…） | **黑体** | **小二 18pt** | 常规 | 对应 Word `Heading 1`（合并版） |
| **一级标题**（一、二、） | **黑体** | **小三 15pt** | 常规 | 对应 Word `Heading 2` |
| **二级小标题**（（一）（二）） | **楷体** | **小三 15pt** | 常规 | Normal 段落 + 15pt（国标楷体分层） |
| **正文** | **宋体** | **小四 12pt** | 常规 | 行距 1.5 倍；首行缩进 2 字符 |
| 列表项 | 宋体 | 小四 12pt | 常规 | 首行不缩进，用悬挂缩进 |
| 表头 | 黑体 | 五号 10.5pt | 常规 | **无底纹** |
| 表内文字 | 宋体 | 五号 10.5pt | 常规 | 行距 1.25 倍 |
| 提示框文字 | 宋体 | 小四 12pt | 常规 | 首行缩进 2 字符 |
| 页码 | 宋体 | 小五 9pt | 常规 | 页脚居中，形式「— X —」 |

> **标题一律不加粗**：中文标题由**黑体本身**承担视觉重量，再加粗属冗余（公文惯例）。
> **颜色**：延续纯黑单色体系（见第五节）。
> **正文口径定案**：正文正式定为 **宋体 · 小四 12pt**（用户 2026-09-10 确认）；此前"仿宋 · 四号 14pt"（2026-08-10 第一轮）**已废止**，不再并行保留，全团按本表执行。
>
> ⚠️ **2026-10-26 再次变更（用户确认 · 方案 A）**：正文中文**恢复为仿宋 · 四号 14pt**（西文宋体）。本节版式条目属"历史存档 · 已由 §0.14 接管"，故以 §0.14 模板与实际生效口径为准——模板 `Normal` 的 `eastAsia` 本就是仿宋，宋体口径与模板自相矛盾，本次予以消除。详见 §2.2 与修订记录。

### 0.2 段落与页面

| 项 | 规范 |
|----|------|
| 首行缩进 | **2 字符**（正文段；12pt 字号对应 **24pt / 480 缇**） |
| 行距 | 正文 1.5 倍；表格 1.25 倍 |
| 页边距 | **上 3.7 / 下 3.5 / 左 2.8 / 右 2.6 cm**（GB/T 9704 版心 156×225mm） |
| 纸张 | A4 |
| 页码 | 页脚居中「— X —」；**封面页与目录页不显示页码**；正文页码从 1 起 |
| 分节 | 封面节 / 目录节 / 正文节 三段，节间自动分页 |
| 表格边框 | 完整表格（Table Grid 全边框）；表头无底纹、仅靠黑体区分 |

### 0.2b 默认输出格式（用户确认 · 2026-09-11）

> **专家团对外交付的默认格式为 `.docx`（Word）**；**PDF 为按需产出**——仅在用户明确要求时才导出。
> 未要求 PDF 时，不导出、也不将其列为待确认项；`build_docx.py` 默认不带 `--pdf`。

### 0.2c 交付命名规范（用户确认 · 2026-09-11）

> 交付文件名统一为：**`方案名称-YYYYMMDD[-VN].docx`**

| 项 | 规则 |
|---|---|
| 方案名称 | 中文全称，不含版本副词（如 `产教融合实训基地解决方案`） |
| 日期 | `-YYYYMMDD`（定稿当日，8 位） |
| 版本号 | 修订版本依次 `-V1`、`-V2`… 以此类推；**当日基线可不带版本号** |
| 历史版本 | 一律移入 `_历史版本/`，**主目录只保留当前交付件** |
| 示例 | 基线 `…解决方案-20260911.docx`；修订 `…解决方案-20260911-V1.docx`、`…-V2.docx` |

### 0.3 结构规范（客户版方案文档）

1. **不设"执行摘要"章节**——客户版方案文档直接从正文第一章开始，**标准方案不含该节**（用户 2026-09-10 确认）。
2. **多部分合一时**：单一封面 + **可点击目录**（由正文标题生成超链接 + 书签）+ 各部分连续成文；各部分标题作为一级标题，内部保持「一、二、…」编号。
3. 层级不超过四级：`一、` → `（一）` → `1.` → `（1）`。

### 0.4 渲染后处理（强制 · 四步，按序执行，缺一不可）

> ⚠️ **通道限定（2026-10-14）**：本节四步为 **tencent-docx（富视觉）通道专用**——**模板基底通道（①editor_sdk / ②build_docx / ③content_to_docx）不执行**（模板通道由样式体系直接保证版式，执行"字体回写/样式清理"反而会破坏模板体系；见 §0.14）。

> 经 tencent-docx 渲染得到的 `.docx` **必须**再按序执行以下三步后处理，否则版式不达标：

| 序 | 步骤 | 脚本 | 作用 |
|----|------|------|------|
| ① | **字体回写** | `scripts/apply_docx_fonts.py <file.docx> [...]` | html-to-docx 的 `apply_cjk_run_properties` 会把**所有含中文的 run 强制刷成正文 CJK 字体**，导致标题的黑体/楷体失效。本步按段落角色回写：`Heading*` → 黑体；首个 `Heading 2` 之前的封面区 → 字号 ≥12pt 用黑体、否则宋体；正文区字号 ≥15pt → 楷体；其余保持宋体 |
| ② | **样式清理** | `scripts/prune_docx_styles.py <file.docx> [...]` | 转换器模板自带 160+ 个**未被引用**的样式，会在 Word 样式面板留下大量冗余条目。本步① 扫描 `document/header/footer` 的实际引用，仅保留被引用样式 + `basedOn/next/link` 闭包 + 必备基础样式，同步裁剪 `word/stylesWithEffects.xml`；② **清理 `latentStyles`**（清空全部 `<w:lsdException>`，并置 `defSemiHidden=1` / `defUnhideWhenUsed=0`）——**只删 `<w:style>` 不够**，latent 声明仍会让 Word 把「标题 3 / 标题 4 / Title / Quote」等未引用内置样式显示在样式面板里 |
| ③ | **表格智能布局** | `scripts/smart_table_layout.py <file.docx> [...]` | 转换器输出的表格列宽默认是**等分**的（如"序号/文件名称/发布主体/时间"四列各 25%），造成窄列挤爆、宽列留白。本步**按列内容显示宽度智能分配列宽**（中文按 2、西文数字按 1，含最小/最大占比夹取）、**表格铺满版心**、**表头跨页重复**（`tblHeader`）、**表头垂直居中**。<br>⚠️ **这是 WPS「表格智能布局」的确定性等价实现**——WPS 该功能为**交互式会员功能，不对外暴露自动化接口**（无 COM ProgID、无命令行入口），无法由脚本点击；如需 WPS 原生效果，只能在**管线产出最终版之后**于 WPS 中手工执行（但需注意 §0.5 第 9 条：应用另存会回退样式清理并改写目录结构） |

| ④ | **表格样式注入** | `scripts/apply_table_style.py <file.docx> [...]` | 为全部表格挂接统一的 Word 表格样式「方案表格」（§0.10），并剥离逐表直接格式，使表格格式可集中管理 |

> 四步均须**读回真实文件核验**（字体集合、样式数量与 `lsdException` 计数、首行缩进、目录链接数、表格列宽占比与 `tblHeader` 数量），不以"脚本执行成功"代替核验。
>
> **适用范围**：① 字体回写**仅适用于 tencent-docx（html-to-docx）通道**——该通道的 CJK 字体注入会覆盖标题字体；② 样式清理与 ③ 表格智能布局**对所有通道适用**（build_docx.py / editor_sdk 通道同样会有样式冗余与等分列宽），建议一并执行。**其余通道不得盲目套用 ①**（其角色判定假设与本文档结构绑定，结构不同时会误判）。
>
> **执行顺序不可颠倒**：③ 会用 python-docx 整体重写文档包，必须放在最后。

### 0.5 已知技术约束（踩坑清单 · docx-agent 必读）

1. **`apply_cjk_run_properties` 覆盖标题字体** → 必须执行 §0.4 ①，否则标题全变宋体。
2. **正文节 class 必须与 CSS 选择器一致**：正文节用 `class="doc-body"`，样式规则须写 `.doc-body`；写错（如 `.report-body`）会**静默失效**，曾导致标题字号停留在 Word 默认值。
3. **标题的字体/字号只能通过内联 `style` 落到 Word 标题段落**；写在 `<style>` 块里的 `h1/h2` 规则不作用于 Word 标题段落。
4. **门禁禁止裸值**：内联样式中的字号/字体族必须写 `var(--fs-h2)` / `var(--ff-heading)` 形式，**不得**写 `15pt` / `黑体`（html-review DT-02/DT-04 会判不通过）。
5. **目标 `.docx` 被 Word 或预览面板占用时**：`os.replace`（重命名替换）报 `PermissionError`；须改为「写临时文件 → `shutil.copyfile` 覆盖 → 删临时」。
6. **首行缩进取值**：`text-indent: 2em` 会被按 12pt 基准解析为 480 缇（≈2.2 字符）；要精确 2 字符（12pt 字号）应直接写 **24pt**。
7. **中文字体可用性**：转换器原生支持 宋体/黑体/仿宋/楷体；"方正小标宋简体"通常未安装，标题如需公文体应退用**黑体**。
8. **只删 `<w:style>` 无法清空样式面板**：`word/styles.xml` 里的 `<w:latentStyles>` / `<w:lsdException>` 会让 Word 把**未被引用的内置样式**（标题 3 / 标题 4 / Title / Quote / Book Title…）照样列在"请选择要应用的格式"中。必须一并清空 lsdException 并把 `defSemiHidden` 置 1、`defUnhideWhenUsed` 置 0（`prune_docx_styles.py` 已内置该步）。**判据**：清理后 `w:lsdException` 计数应为 0，样式面板只应出现实际在用的 5~7 项（正文 / 标题 1 / 标题 2 / 列表编号 / 列表项目符号 / 页脚 / 默认段落字体）。
9. **交付件不要用 Word / WPS 直接"打开→另存"**：两者另存都会 ① 把 `w:styleId` 规范化成纯数字 ID、② 重新引入完整的 `latentStyles`（把 ② 步清掉的冗余样式又带回来）、③ 改写目录结构（Word 会把 `w:hyperlink w:anchor` 变成纯文本**导致目录失去跳转**；WPS 会改写成 `HYPERLINK \l "_Toc_xxx"` **域**——仍可点击但结构已变）。**判别是否被应用另存**：读 `docProps/app.xml` 的 `<Application>`（如 `WPS Office_12.1.0.28505` / `Microsoft Office Word`）。**客户/同事用 Word/WPS 改过的交付件，应回到本管线重渲后覆盖**，不要在其基础上继续加工。
10. **表格列宽默认等分，必须执行 §0.4 ③**：转换器给每张表的列宽都是等分的（`tblGrid` 各列相同），对"序号/名称/主体/时间"这类宽窄悬殊的表观感很差；`tblW=pct 5000` + 固定 `tcW` 还会让"自动调整"失效。
11. **文件被占用时的写回**：`shutil.copyfile` 与 `os.replace` 在目标被 Word / WPS / 预览面板 / 同步盘占用时都可能失败（前者 Permission denied、后者 WinError 5）；此时**先请用户关闭该文档、或等待同步盘释放（加 3 秒间隔重试 5~6 次）**，再重跑后处理，**不要静默跳过**（否则只有部分步骤完成，出现版本不一致）。
12. **正文不得用制表符/框线字符画结构图**：`┌ ─ ┴ ┐ │ └ ┘ ├ ┤` 这类 ASCII 框线**依赖等宽对齐**，而 Word/WPS 正文用宋体（中西文字宽不等），渲染后必然错位，读起来"是乱的"。**结构图一律改用表格表达**（如"层级 / 组织构成 / 主要职责"三列），层级关系（决策层 → 推进层 → 执行层）用"层级"列的文字体现；**流程**用单行"`A → B → C`"表达（可放在 callout 内）。**判据**：交付 .docx 的 `document.xml` 中框线字符计数应为 **0**。
13. **表格内文字不在 `document.paragraphs` 里**：核验时若用 python-docx 遍历 `document.paragraphs` 找关键词，**会漏掉所有表格单元格内容**，造成"内容缺失"的误判；核验表格内容须遍历 `document.tables[*].rows[*].cells`，或直接 grep `word/document.xml`。
14. **文字处理组件（Word COM）异常后必须确认进程退出**（PR-006）：组件调用异常退出时可能留下无窗口的后台进程，持续锁定交付文件（表现为"文件被占用"长时间不释放）；操作后应检查并清理残留进程，再进行文件替换。
15. **目录（域）维护**（PR-006）：更新目录域时**不要删除域所在段落**（删除会破坏域结构）；应使用"更新域"刷新条目，页码与条目随正文自动重算。

### 0.6 客户版解决方案文档的推荐架构（四段式 · 用户确认）

> 面向院校/客户的解决方案正文，默认采用**四段式**架构，且四段之间建立**一一对应**：

```
一、项目目标      二、项目内容      三、实施方案      四、预期成果
```

**一一对应的三处机制（缺一不可）**：

1. **项目目标分解表**：把总目标拆为 3~5 项**项目目标**（编号 目标一…），逐条给出「目标表述 + 目标内涵」；项目目标应从方案既有叙事中提炼（如"人人能练 / 练什么、怎么评 / 越练越强"三句价值排序 + 体系可持续），**不另造新目标**。
2. **对应总表（4×N 矩阵）**：置于「项目目标」末尾，横向列出 `项目目标 | 对应项目内容 | 对应实施方案 | 对应预期成果`；跨目标的支撑性内容以「跨目标」行单列。
3. **小节后缀标注**：在「项目内容」「实施方案」「预期成果」三部分内，**每个小节标题后缀标注「（对应目标X）」**，使任一部分都能与目标对上号。

**重排纪律（原文不改）**：
- 重排是**结构搬运**：原有表述与内容**一字不改**，只做位置调整、标题重编号、增加对应标注与总表。
- **必须机器自检"实质漏项 = 0"**：对原 md 与新 md 做段落集合比对，差异只允许出现在标题行（被重命名/重编号者）；出现非标题类漏项即视为失败，须补回。
- 章节导语（H2 与首个（一）之间的段落）极易在搬运中丢失，**逐章核对导语是否已归位**。
- 推荐用脚本完成重排（可复用 `scripts/` 同类实现），而非手工剪切，以保证不漏段。

### 0.7 交付口吻：只写已确认内容（用户确认 · 硬规则）

> **客户版方案文档是"对外承诺性文件"，不是草稿或讨论稿。** 正文一律采用**宣告式**表述，**禁止出现商量、建议、待定性质的话术**。

**禁止出现的表述类型（示例）**：
- ❌ "建议按…三层设定" / "建议采用…路线" / "建议以三层组织承载" → ✅ "本方案按…三层设定" / "本方案采用…路线" / "本方案以三层组织承载"
- ❌ "以下目标值为**建议值**，最终由院校与实施方在启动阶段共同确认" → ✅ 删除该句（目标值即方案目标值）
- ❌ 表头"目标值（建议）""建议配置""建议权属/建议归属" → ✅ "目标值""配置""权属/归属"
- ❌ "以正式产品清单为准""须与院校共同建立，最终以双方确认的制度为准" → ✅ 由用户确认口径后写实，或删除
- ❌ "建议明确响应时限…""建议以 POC 验证" → ✅ 由用户给出确定口径后写实

**与红线的关系（重要）**：
- 红线的实质是"**不得把未验证的能力/价格写成已确认**"。落实方式**不是**加 hedge 话术，而是**回问客户**：
  - 凡口径未定 → **必须向用户（客户方）提问**，列出"需要确认项 + 建议选项"，**不得自行用"建议/待确认/以…为准"兜底**；
  - 用户答复后 → 按答复**写实**（宣告式），并在回复中标注该项为「客户已确认」；
  - 用户答复"确实未定" → 该项从正文移除或改为范围性陈述（如"第三层为预留发展目标"），**不保留商量话术**。
- 禁止的是**话术**，不是**诚实**；两者不可混淆。

**执行纪律**：
- 清洗须**全量盘点**后再动手：`建议 / 待确认 / 需确认 / 假设 / 示意 / 非报价 / 以…为准 / POC / 未验证 / 规划中 / 预留 / 可协商 / 视情况 / 待补` 逐类统计处数，避免漏改。
- 文本替换**长规则优先**（短规则先跑会污染长规则，如 `建议采用` 会把"并建议采用报价分档"改成"并本方案采用…"）；改完须**回扫语病**。
- 清洗后须复跑全量盘点，**目标：商量类表述计数为 0**（保留项须逐条说明理由）。

### 0.8 线性流转内容的表达规范（用户确认）

> 方案里大量存在"A → B → C"式的**线性流转/数据传递**内容（环节链、递进链、闭环链）。**单行箭头长串禁用**（7+ 环节挤在一行、密而难读、也无法标注回流）。按内容类型选下面两种表达：

| 方式 | 形态 | 适用判据 | 实现 |
|------|------|----------|------|
| **方式一　横向流程条** | 表格：每格一步、格内「序号 + 环节」；≤4 步用 1 行，5~8 步折 2 行（每行 4 格） | **环节标签短**（≤8 字/步）、纯先后关系 | Markdown 单行表（首行为数据、无表头）→ 渲染为无表头表格；**闭环链**末格加 `↺`（如"⑦ ↺ 下一轮训练"） |
| **方式二　环节—输入—输出表** | 三列表：`环节 \| 输入 \| 输出` | **有明确数据传递**的链路；输入 = 上一环节的输出 | 标准 Markdown 表（3 列） |

**保持原样（不改造）**：
- **句内嵌链**（如"让学生真正经历任务分析 → 数据设计 → …"、"具备'任务 → 数据 → 模型 → 机器人 → 反馈'完整工程方法"）——嵌在句子里的链拆出来会打断行文；
- **表格单元格内的链**（如授权流程、能力架构表中的链）；
- **3~5 个名词的短标签引用**。

**禁止**：① 用制表符/框线字符画流程（见 §0.5 第 12 条）；② 用图片流程图（不可编辑、与全表格风格不一致，改一处要重绘）。

**工程要点**：
- 1 行表格必须渲染为**无表头表格**（`<table><tbody><tr>`），否则会变成表头样式；`md2html.py` / `merge2html.py` 已支持"仅 1 行 → tbody"。
- 流程条的列宽由 §0.4 ③ 表格智能布局按内容自动分配，无需手工设宽。
- 改造后须核对：原句语义未变、未漏字；句内链未被误拆。

### 0.10 表格统一样式（用户确认 · 2026-09-11）

> **所有表格必须引用同一个 Word 表格样式**，不得依赖逐表直接格式——否则改一处要动全部表。样式名 **「方案表格」**（styleId `SolutionTable`），由 `scripts/apply_table_style.py` 注入。

| 属性 | 取值（用户口径） |
|---|---|
| 边框 | **全边框**：外框 1.0pt（sz=8）＋ 内线 0.5pt（sz=4），色 #BFBFBF |
| 表头行 | **黑体** 小四 12pt、**无底纹**、垂直居中、左对齐、跨页重复（`tblStylePr w:type="firstRow"`） |
| 数据行 | **宋体** 小四 12pt（**字体字号与正文一致**）、垂直居中、左对齐 |
| 单元格边距 | 上 28 缇 / 下 **120 缇** / 左右 85 缇 |
| 表格宽度 | 100% 版心 |
| 行距 | 单倍（表格内不随正文 1.5 倍） |
| 表格后间距 | 由**下单元格边距 120 缇**（≈ 0.5 行）统一给出，解决“表格下紧跟正文过近”问题 |

**实施要点（缺一不可）**：
1. **必须真正剥离直接格式**，否则样式不生效（直接格式优先级高于样式）：删 `tcBorders` / `tblBorders` / `tblCellMar` / `tblW` / `tblInd` / 表内 `rFonts·sz·szCs` / `tcPr` 的 `shd`。
2. **保留实例属性**：`tblGrid`（列宽，来自 §0.4③ 表格智能布局）、`tblLayout`、行属性 `tblHeader`、单元格 `tcW`。
3. **XML 子元素顺序必须合 schema**（顺序错 Word 报"文件损坏"）：`w:style` 内 `name → basedOn → uiPriority → qFormat → pPr → rPr → tblPr → tcPr → tblStylePr`；`tblPr` 内 `tblW → tblBorders → tblLayout → tblCellMar`；`w:tblStyle` 必须是实例 `tblPr` 的**第一个**子元素。
4. **后处理升级为四步**：① 字体回写 → ② 样式清理 → ③ 表格智能布局 → **④ 表格样式注入（最后一步）**。
5. **验收 5 条断言**：样式存在且名「方案表格」；表数 = 挂接数（100%）；六类直接格式残留 = 0；列宽合计与 `tblHeader` 数不变；**改样式一处即全表联动**。

**配套段落样式「表格文字」（用户确认 · 2026-09-11）**：

| 项 | 口径 |
|---|---|
| 类型 | **段落样式**（会出现在 Word/WPS 的「样式」窗格中，可一键套用） |
| 字体字号 | **宋体 · 小四 12pt**（与正文一致） |
| 行距 | **1.5 倍** |
| 其他 | 左对齐、**首行不缩进**、基于 Normal |

- **套用范围**：全部**数据行**单元格段落（本次 1041 处）；**表头行不套**——表头保留「方案表格」表格样式 `tblStylePr(firstRow)` 给的黑体，避免段落样式优先级盖掉黑体。
- **职责分工**：**格式归属**由「方案表格」（表格样式）管边框/边距/表头；**文字归属**由「表格文字」（段落样式）管字体字号行距；两者同为「改一处、全表联动」。
- **⚠️ 表格样式为什么不在右侧窗格**：Word/WPS 的「样式与格式」窗格**只列段落样式与字符样式**，表格样式不在其中（这是软件分类设计，无入口）。表格样式的查看/管理入口是：**选中表格 → 「表格样式」选项卡/库**；或样式窗格「选项…」→ 显示范围改为「全部样式」。**"在右侧窗格新增一个表格样式"在软件层面不可实现**，落地方案即"表格样式 + 表格文字段落样式"组合。
- **⚠️ 重复插入防护**：向 `tblPr` 插 `w:tblStyle` 前须先清除已有同类节点（`tblPr` 内 `tblStyle` 仅允许 1 个），否则会变成 2 份引用、schema 违规。

**"集中管理"的验证方法**：只改 `styles.xml` 中 `SolutionTable` 的一处（如边框 `sz` 或表头字号）→ 重开文档 → 全部表格同步变化（改一处、生效果），证明样式确为唯一格式来源。

## 四、标题层级与编号规则

### 4.1 层级深度

> **问题**：售前方案文档需要几级标题？默认 H1/H2/H3 三级，是否需要 H4/H5？

| 层级 | 是否启用 | 编号格式 | 状态 |
|------|----------|----------|------|
| H1 | 是 | 一、二、三…（汉字数字 + 顿号） | 【已确认：见 doc-tree-spec.md】 |
| H2 | 是 | （一）（二）（三）…（汉字数字 + 圆括号） | 【已确认 · 用户答复 2026-08-10】 |
| H3 | 是 | 1. 2. 3.…（阿拉伯数字 + 句号） | 【已确认 · 用户答复 2026-08-10】 |
| H4 | **启用 · 小四 12pt** | （1）（2）（3）…（阿拉伯数字 + 圆括号） | 【已确认 · 用户答复 2026-08-10】 |

#### 编号实现机制（硬要求 · 套用模板自动编号）

> **本条款为对外正式文档（模板基底通道）的强制规则：`docx-agent` 与 `build_docx.py` 均须遵守；以标准模板 `assets/样式模板.dotx` 为准（§0.14）。**

1. **自动编号来源唯一**：标题序号**完全由标准模板 `assets/样式模板.dotx` 的 `heading` 样式内置 `numPr` 自动生成**（六级：一 → 1.1 → 1.1.1 → 1. → 1） → ①），不依赖脚本或 LLM 拼接。
2. **JSON `section.title` 严禁手写编号**：docx-agent 组织的文档树里，所有 `title` 必须是纯标题文本，**不得包含** `一、` `（一）` `1.` `(1)` `①` `第X、` 等任何序号前缀。`build_docx.py` 虽做防御性剥离，但应以 JSON 干净为前提。
3. **禁止双重编号**：脚本对 `numbering="auto"` 的章节仅套用模板 `heading` 样式（其 numPr 生效），绝不手动拼接前缀；对 `numbering="none"` 的章节（如附录标题）套用同一样式但移除 numPr。二者都不会产生"一、一、"式重复。
4. **页边距/字号/行距硬继承**：build_docx.py 继承标准模板 `sectPr` 与样式体系（**A4；上/下 2.54 cm、左/右 3.18 cm**；字号/行距由模板样式定义），**不覆盖、不回退**。
   > ✅ **模板口径提示（2026-10-14）**：原『`文字文稿1.dotx` 为旧口径、使用前须按 §0.1 校准』提示**已失效**——对外正式文档统一以 `assets/样式模板.dotx` 为基底（终态口径，无需校准）；以配套规范 `word-template-style-spec.md` 为生成指引（内容映射与编号清洗见其 §6.7）。
