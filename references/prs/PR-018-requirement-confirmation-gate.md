## 一、起因与目标

用户诉求（原文要点）：**"写文档要多问我问题，确认好需求以后再干活儿。"**

现状缺口：团长 SOP 从 G0 任务形态判定直接进入 TeamCreate 与 Phase 0，缺少"开工前向用户确认交付方向"的环节。写文档/报告/方案类任务若在受众、用途、范围、格式、口径、验收标准未定的情况下开工，全链成员围绕错误假设运转，末端集中返工。既有的 §6.4「澄清问题规范」与 §6.5「决策呈交」是**研究阶段/变更阶段**的局部规则，不覆盖"开工前总闸门"。

目标：在建立团队之前设置一道**可验收的硬闸门 G-1**，把用户要求固化为判据，而不是一句提醒。

## 三、G-1 设计判据（可数、可执行）

- **职责判定**：团长开工前亲自问；未过闸禁止 TeamCreate / 调度成员 / 写正文；交付方向歧义由用户拍板；六要素齐全且用户明示"不用问"时可豁免并复述六要素。
- **六类必问要素**：交付物与形态 / 受众与用途 / 范围与重点 / 素材与口径 / 约束与红线 / 验收标准。
- **提问规格**：一次 ≤5 问、选项化、只问会改变交付方向的真歧义、支持"先出大纲确认"。
- **输出规范**：需求确认简报 RB v1 作为交接物首字段常驻 L1；六要素全部有值 + 用户明确确认 + RB 写入交接物 = 放行。
- **知识检索与引用纪律**：RB 涉及既有口径须引用 `references/` 真相源并标注；用户新口径标「用户拍板·时间」；推断不得写成已确认。

## 四、证据与依据

- 用户直接诉求（本轮会话）：写文档多问问题、确认需求后再干活。
- 既有依据：团长 §6.4 澄清问题规范（最多 3 个、只问真歧义、选项化）、§6.5 客户澄清前置与决策呈交、communication-protocol.md §二「决策上交」三问——G-1 与三者同向，不冲突，仅上移为开工前总闸。
- 一致性核对：G-1 未改动 tags / quickPrompts / displayName / expertType / categoryId 等展示标识字段；未改 name / agentName / 目录名 / 成员 MD 文件名。
