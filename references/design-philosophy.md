## 0. 一句话定位
本专家团 = **不共享上下文（进程式隔离）＋ 管理者模式（ORCH = Manager）＋ 显式 handoff（交接物 = 上下文交接物）** 的多 Agent 系统。这一组合在《AI Agent》第 10 章被论证为"上下文会快速膨胀 / 需要隔离 / 需要并行 / 信息损耗非硬约束"场景的最优解——恰好覆盖售前方案场景。

## 1. 上下文是否共享（Ch.10.1）
- 书中两态：**共享上下文**＝继承式（线程比喻，信息零损耗但膨胀快）；**不共享上下文**＝隔离式（进程比喻，显式交接、模块化、易扩展）。
- 我们的选择：**不共享上下文**。
  - 每个成员是独立 Agent 实例，持有自己的上下文窗口（＝进程的内存）；
  - 信息经**上下文交接物（Handoff Artifact）** 显式传递，而非继承前任完整轨迹；
  - 收益：模块化、可并行、隔离彻底（一个成员出错不污染其他成员）、调试可定位。
- 代价（书中已指出）：信息同步复杂 → 我们用「结构化交接物 ＋ 引用标签 ＋ 团长中转」解决：团长侧维护完整可追溯链（L2），下发只给最小必要子集（L0/L1）。
- **附带红利（书中「思维惯性」思考题）**：不共享上下文时，下游看不到上游"思考过程"，反而避免了上游角色偏见渗透（如需求分析师视角污染代码审查）。我们"引用上游结论标签而非喂完整轨迹"的方式，天然规避角色间干扰。

## 2. 协作拓扑（Ch.10.1.2 / 10.4）
- 我们采用**管理者模式（Orchestration Pattern）**：ORCH 作中心化 Manager 负责规划与调度，11 个成员为专业子 Agent。对等 / 去中心化模式不适用（售前场景需中心化质量门控）。
- 书中要点：
  - **Manager 的能力上限＝系统能力上限** → 我们把最强、最精心设计的提示词给 ORCH（`team-lead.md` 本身即最厚重的文件）。
  - **预算感知**：Manager 应按子任务复杂度动态分配步骤 / Token 预算（书中 BAVT）→ 对应「团长工程纪律」中的产物版本锁、确定性闸、按任务复杂度分配。

## 3. 通信机制 ＝ 进程间通信 IPC（Ch.10.1 / 表 10-3）
- 书中：Agent 间通信落在两大范式——**共享内存**（文件系统）＋ **消息传递**（工具参数 / 消息总线）。操作系统类比：程序＝静态前缀，内存＝轨迹，CPU＝LLM，fork＝spawn_subagent，kill＝cancel_subagent，ps＝list_agents。
- 我们的映射：
  - **共享文件系统（数据平面）**：项目工作区 `embossed_projects/<project_id>/`（＝多 Agent 共享空间，持久化、需并发控制）＋ `references/`、`scripts/`、`*.md`（＝系统内置资源，全局只读、跨会话稳定、渐进式披露）。
  - **消息传递（控制平面）**：团长↔成员的 `SendMessage`（＝消息总线形态，带 `type` 字段的信封）；交接物本身作为"工具调用参数"式的结构化数据传递。
  - **信封（envelope）**：`SendMessage` 带 `type`（message / shutdown_request / plan_approval_response），对应书中"发送者 ID / 目标 / 消息类型 / JSON 负载"的结构化信封，保证链路可追踪。

## 4. 虚拟文件系统四区（Ch.10.4.1）→ 我们的存储分层
- 书中：Agent 眼中的文件系统是挂载了四类区域的虚拟目录树——① Agent 专属工作区(Scratchpad) ② 多 Agent 共享空间 ③ 外部挂载资源 ④ 系统内置资源(只读)。
- 我们精准对应：
  - ① **Scratchpad** ＝ 每个成员 Agent 的**独立上下文窗口**（私有、随实例销毁、不并发控制）。
  - ② **共享空间** ＝ `embossed_projects/<project_id>/`（用户可见、持久化、需并发控制 → 故强制"派新即关旧 ＋ 磁盘唯一事实底座"，防并发写覆盖）。
  - ③ **外部挂载** ＝ 客户提供的多源材料（PPT/PDF/Word…），经 `doc-in-agent` 适配为结构化输入。
  - ④ **系统内置资源** ＝ `references/`（`redlines.md`/`knowledge-index.md`/`governance.md`/`input-spec.md`/`project-context-spec.md`/`doc-tree-spec.md`）＋ `scripts/`，**全局只读、跨会话稳定、渐进式披露（成员按 L0/L1/L2 按需取用）**。这正是书中"默认隔离、共享须显式声明"——`references/` 是显式声明为全员共享的只读段。

## 5. 上下文腐化与按需最小化下发（Ch.2.7）
- 书中：**上下文腐化（Context Rot）**——窗口未溢出也会因无关内容占大头而决策质量悄然下降；应主动、显式地做知识提炼，而非指望模型从冗长上下文中自动学习。注意力机制"擅长检索、不擅长归纳统计"。
- 我们：`§2.2 按需最小化下发` ＋ `L0/L1/L2 三层加载` 直接对应。团长默认只下发 L0+L1（≈2k tokens），被裁剪历史经引用标签（`【依据 <member-id>:<结论标签>】`）按需取用。这把"检索而非推理"的注意力短板交给显式提炼补全，避免下游被无关上下文稀释。

## 6. KV-Cache 友好的静态前缀（Ch.2.3 / 4.8）
- 书中：静态前缀（系统提示词＋工具定义）字节级不变 → KV Cache 持续命中；变动内容追加到轨迹末尾而非前置。
- 我们：每个 agent 的 `.md` 即稳定静态前缀；交接物作为新内容追加下发、前缀不动 → 缓存稳定、首 Token 延迟低。若未来引入动态工具（脚本 / 外部 MCP），须追加到末尾、不得重排已加载项（见 §6.5 工程纪律）。

## 7. 渐进式披露 / Skills（Ch.2.5 / 4.8.2）
- 书中：Skills 把完整知识从常驻上下文改为"薄目录 ＋ 按需查阅"，更接近人用工具书；模型原生全量注入在大上下文下指令遵循退化。

## 8. 失败模式防御（Ch.10.5 MAST ＋ 工程视角）
- 书中：MAST 分类法归纳 14 种多 Agent 失败模式，分三类——**系统设计缺陷 / Agent 间对齐失败 / 任务验证缺失**。Agent 故障是**拜占庭式**（继续给看似可信的错误结论、不主动声明错误），故需独立冗余去发现。两种工程视角失败模式最致命：① 共享文件系统的并发冲突 ② 错误的级联放大。
- 我们对齐：
  - **并发冲突（文件级丢失更新 / 跨文件语义冲突）** → 防覆盖三件套：**派新即关旧**（向旧实例发 `shutdown_request`）、**磁盘唯一事实底座**（dat 落盘后团长重读磁盘权威数字）、**M4 版本锁 ＋ 语义一致性检查**（`check_budget_consistency.py`）。读多写少区（`references/`）设为**只读**，从根上消除写冲突；写多的共享空间（项目工作区）靠"派新即关旧"实现 worktree 式隔离。
  - **错误级联放大（语义逐层失真）** → ver-agent 的**独立交叉验证**：ver **只看原始证据 ＋ 最终结论，不看前序 Agent 思考过程**（书中"交叉验证不看前序思考过程，只看原始证据和最终结论是否一致"）。上游一个术语 / 事实错误不会因"下游一致采用"而被误判为正确。对应 ver 的「异源互审 ＋ 多源异构评判」。
  - **任务验证缺失** → ver 外发闸门 ＋ **确定性工具反馈**（`verify_text_count.py` / `check_budget_consistency.py`）。书中："确定性外部反馈（测试 / 编译器 / 数据库查询）是系统里唯一不会说谎的部件"——我们把脚本作为 ver 的"不会说谎"断链器。
  - **过早终止 / 假成功** → 验收四维度 ＋ ver 判定的"可进入使用 / 修订后复核 / 禁止外发"三态；完成与否由扎根真实观测的验证器判定，而非成员自报。

## 9. 多 Agent 优于单 Agent 的判据（Ch.10.2）
- 书中核心判据：协作是否引入生成时**不存在的新信息**。若只是多 Agent 看同一段文本互审（辩论），等量算力下不优于单 Agent；但若 Reviewer 获得外部反馈（执行结果 / 视觉渲染 / 工具验证），优势实质。
- 我们：专家团的价值正在于此——每个成员带来**领域专精的新视角**（ind/pol/cus/pro…），且 ver 引入**确定性工具反馈**（脚本 / 版本锁）。这是用团队而非单 Agent 的根本理由，也是"团长不替成员补结论"原则的依据：补写会丢失专业视角的独立性。

## 10. 工具与信任边界（Ch.4 投毒防御）
- 书中：接入第三方 MCP / 工具＝引入新信任边界；须防**工具描述投毒（tool description poisoning）**、**工具遮蔽（tool shadowing）**、**凭证泄露**；底线是**参数传递保真性**（模型感知的世界 ≠ 工具操作的世界不能有系统偏差）。
- 我们：当前 `references/` 是**单一信任源**，不接外部 MCP，成员不得自写红线 / 知识副本（§2.3 中央真相源纪律）。若未来接入外部工具 / 知识源，须经 `governance.md` 的 PR＋异源互审，且运行时做"预览 ＋ 人工确认"的最小权限控制。隐私级别闸（ver 模块）对应"访问私有数据 / 暴露于不可信内容 / 对外通信"三要素最小权限。

## 11. 状态查询、执行终止与资源调度（Ch.10.4.2）
- 书中：① **状态查询**——用消息问答或读进度文件 / 轨迹（JSONL），进度文件最后修改时间超阈值即判卡住；② **执行终止**——优雅（SIGTERM 式：循环中查终止信号）vs 强制（SIGKILL 式）；终止沿创建关系向下级联（无孤儿 Agent）；③ **资源调度**——步数 / Token 预算，超限即止，困难任务给强模型。
- 我们映射：`SendMessage` `shutdown_request` ＝ 优雅终止信号，旧实例须在循环中响应；**派新即关旧** ＝ 级联终止纪律，杜绝后台旧实例回写（孤儿 Agent）；卡住检测 ＝ 工程纪律中"产物版本锁 ＋ 重读磁盘"；预算 ＝ 团长按任务复杂度分配确定性闸。

## 13. 第 1 章 Agent 入门 → 团队的最小定义与学习载体（Ch.1.1）
- **Agent 恒等式**：Agent ＝ LLM（大脑）＋ 上下文（记忆/状态）＋ 工具（手脚）。我们精准对应：11 位成员＝LLM；交接物＋项目工作区＝上下文；`SendMessage` / `scripts/`＝工具。
- **观察空间 / 动作空间**：书中"产品能力演进＝观察空间与动作空间的演进"。对应我们的**渐进式披露**：先用最窄接口（L0 红线摘要）起步，随任务复杂度扩展（L1/L2 全文）→ 与 Ch.1.1"先最窄工具、随复杂度扩展"的工具设计原则同构。
- **三路径学习（图 1-1，与 Ch.8 图 8-3 完全对齐）**：行为改变发生在三个互补位置——
  - 任务内适应（Context adaptation，载体＝当前上下文，即时、任务结束不保留）→ 我们的 **L0/L1/L2＋交接物**；
  - 外部制品更新（External artifacts，载体＝知识/指令/程序，跨任务持久、可审计）→ 我们的 **`references/`＋ agent `.md`＋ `scripts/`**；
  - 参数更新（训练周期）→ **当前不用**（由 Ch.7 论证为何不微调）。
  - 这是团队"零训练、以外部制品承载硬约束"的根本理论依据。
- **Model as Agent ＋ Harness ＝ 缰绳与挽具（Ch.1.1.3.1）**：模型越强大，外围 Harness 越关键；模型自主决策空间越大，越需精细约束/验证/纠正。我们的 **ORCH＋交接物＋验收四维度＋外发闸门**＝Harness 工程外壳（"模型做不稳的，Harness 先补上"）。
- **《苦涩的教训》（Ch.1.1.3.1）**：方向认同、节奏务实。模型会持续内化 Harness（工具调用、长程规划早已是原生能力），但"吃"比直觉慢、无法一次内化所有业务约束与偏好 → 我们"以 `references/` 承载不可变红线与事实、而非靠模型记忆"正是对 Bitter Lesson 的工程实践，呼应 §10 工具信任边界。

## 14. 第 3 章 用户记忆与知识库 → cus 画像、知识检索与知识治理（Ch.3.1 / 3.2 / 3.3）

  - 记忆存储层整理算法（筛选/聚类/抽象/版本化/冲突检测：某些信息只保留最新版、某些保留完整历史）→ 对应 `governance.md` 三分层（原始证据/知识/服务）＋ 定期整理例程。

  - 映射：`knowledge-index.md` 为检索入口；应用内 `tfidf.ts` / `ragClient.ts` 当前实现为**稀疏(TF-IDF)＋本地知识回退**的轻量 MVP。
  - **诚实边界（已知工程债）**：书明确"没有单一检索策略全可靠，稠密＋稀疏＋重排序才是生产级"。我们当前未上稠密向量与重排序器，属已知短板，生产级需补（不夸大当前能力）。
- **3.3 超越扁平文本**：RAPTOR / GraphRAG 结构化索引、OpenViking 文件系统范式 L0/L1/L2（已落地 §2.1）、知识更新 PR＋异源互审＋睡眠学习＋失效内容版本化下线（已落地 `governance.md`）、智能体化 RAG、上下文感知检索（补充分块切断上下文的固有缺陷）、结构化数据提取。
  - **上下文感知检索**直接对应我们的**引用标签机制**（`【依据 <member-id>:<标签>】`）：被切分的交接物通过标签携带上游结论上下文，弥补分块式传递的上下文断裂——与书"分块会切断片段与原始上下文联系"的伏笔正好正面对接。

## 15. 第 5 章 Coding Agent 与通用 Agent → 文件系统中枢与"代码即元能力"（Ch.5.1 / 5.2）
- **5.1 Coding Agent**：文件系统作为信息中枢（`MEMORY.md` / `SOUL.md` / `CLAUDE.md` / `AGENTS.md` / `.cursorrules`＋ Git 版本化）＋ 7 核心工具（读/写/编辑/搜索/执行/版本/浏览器）。

- **5.2 代码作为元能力**：业务规则编码化（约束写进代码而非文档）、测试驱动、自我修改、工具创造、最小权限、忠诚度光谱（prompt injection＝叛变；语义解析而非关键词黑名单；参数传递保真性）。
  - 映射：`scripts/`（`check_budget_consistency.py` 等）正是**"业务规则编码化为确定性约束"**；ver 隐私级别闸＝**最小权限**；Ch.4 工具"参数传递保真性"＝忠诚度光谱的语义解析——"模型感知的世界 ≠ 工具操作的世界不能有系统偏差"。

## 16. 第 7+8 章 后训练与持续进化 → 四载体模型与三层验证（Ch.7.13 / 8.1 / 8.2）
- **7.13 核心结论**：SFT 记忆、RL 泛化；先 SFT 稳定格式再 RL 探索；**数据和环境比算法更重要**；**陷阱①：过度依赖后训练记忆事实 → 用 RAG 管理事实（动态更新、可追溯、不因训练遗忘），后训练聚焦"如何使用知识"**；ICL / RAG / 程序 / 参数 四载体协同（Ch.7.13 末段）。
- **8 持续进化**：三层验证（结果验证器 / 过程验证器 / 质量验证器，图 8-2）＋ 四种更新方式（知识 / 指令 / 程序 / 参数，图 8-3）＋ 闭环（记录轨迹→形成信号→生成候选更新→验证发布→回归灰度回滚）。
- **四载体模型直接映射团队架构**（这是"零训练"路线的理论背书）：
  | 载体 | 书中定位 | 团队落点 |
  |------|----------|----------|
  | RAG | 事实与证据，可动态更新、可追溯 | `knowledge-index.md` / `references/` |
  | ICL | 零参数即时适应（随上下文增长延迟↑） | 交接物 ＋ L0/L1/L2（任务内上下文适应） |
  | 程序 | 确定性流程与硬约束 | `scripts/`（ver 的"不会说谎"断链器） |
  | 参数 | 高维感知 / 生成风格 / 隐式策略 | **当前不用**（能力均能被事实/语言/程序表达，按 Ch.8 标准本就选前三载体） |
- **"保存经历 ≠ 从经历中学习"** → ver 独立交叉验证（不看前序思考过程、只看原始证据＋结论）；**"验证器只给评价与证据，修改哪个部分由独立诊断模块决定、避免既当裁判又改规则"** → ver（裁判）与 ORCH / `governance.md`（决策）职责分离。
- 结论：专家团刻意**不微调**，而用 `references/`（RAG 式事实库）＋ 交接物（ICL 式适应）＋ `scripts/`（程序式硬约束）三载体，正是 Ch.7/8 明确推荐的稳健系统组合。

## 17. 第 9 章 多模态与实时交互 → 规划-执行-验证三元结构（Ch.9.8 / 9.9）
- **9.8 Computer Use**：感知-思考-行动循环（截图→推理→执行→再截图）＋ 动作空间四类工具（GUI / 感知 / bash / 文件编辑）＋ 视觉定位（Set-of-Mark 选择题 vs 纯坐标预测）＋ 坐标缩放（模型感知分辨率 ≠ 真实分辨率需双向映射）。
  - 映射：① 感知-思考-行动循环＝ 我们"下发交接物→成员回传→团长验收"循环的镜像；② **"通用基础能力 vs 高风险专用受控工具"原则**（通用 Python 沙盒 vs 支付/删除等须预览＋人工确认）→ 我们"通用脚本 vs 高风险动作须人工确认"；③ 坐标缩放＝ 接口保真性（模型感知世界 ≠ 工具操作世界，呼应 Ch.4 / Ch.5.2 忠诚度光谱）。
- **9.9 机器人操作**：双层架构（长程规划慢决策 / VLA 控制快执行）＋ 动作分块（拿反应换平滑）＋ 流式执行（command 事件 ＋ 每步验证 ＋ 背压）＋ 世界模型（先预测后果再行动）＋ "把事实写回世界状态而非仅追加自然语言"。
  - 映射：① 双层架构＝ ORCH（规划）vs 成员（执行）职责分离，与"派新即关旧"实例隔离呼应；② 流式执行"只有语法完整、参数齐全、通过校验的 command 才能提交"＝ 结构化交接物 ＋ 验收四维度；③ **"执行一步验证一步、保留已验证前缀、作废失效后缀"**＝ 变更 v<N> 版本纪律 ＋ "已确认结论不静默覆盖"；④ 世界模型"先在脑中试做"＝ mat「先判断后方案」＋ ver「先在真值层验证」；⑤ "把事实写回世界状态"＝ ProjectContext 信封单例 ＋ `context.json` 唯一真相源。
- **边界声明**：Computer Use / 机器人属"多模态 / 具身控制"通道，超出本售前文本方案团队的接口范畴（观察空间＝文本/文档，动作空间＝结构化交接物＋文档落盘）。其"规划-执行-验证"三元结构与我们的 SOP 同构，可作为**类比锚点**而非直接依赖。
