# 沟通协议（Communication Protocol）

> **中央真相源**（2026-10-26 定版，用户确认）。定义团长与成员之间**什么该传、传多长、传几轮、什么时候停**。
> 团长 §3.3 引用本文件；成员**在回传前自检**，不达标即自行重写，不要交给团长打回。
>
> **立此协议的起因**：某次交付中，成员回传大量"我撤回上一条""我自报我文件的缺陷""我给规则加护栏"之类**过程性内容**，占该次协作 token 的约三成，而交付物本身没变。根因不是成员不守规矩，是**没有规定什么算合格回传**。

---

## 一、一条回传只允许四段（超出即重写）

| 段 | 写法 | 上限 |
|---|---|---|
| **结论** | 分条，每条一句，带结论标签（如 `ind:利好#3`） | ≤ 5 条 / 150 字 |
| **依据** | 每条结论对应一个出处：政策号 / 文件页码 / 上游标签 / 数据源 | 逐条一句 |
| **待确认** | 只写"卡住我结论的那一个问题"，不问泛泛的开放问题 | ≤ 3 条 |
| **状态** | 一行：阶段 / 产物版本 / 未闭合项数 | 一行 |

**长度是判断力的代理指标**：超过 **800 字**或 **6 条结论**，**退回重写而非压缩**——超标通常说明没分清主次，压缩只会把没想清的部分藏起来。

> 回传里**不写**：目录、章节导读、自我评价、与上一版的逐条差异表（除非团长点名要）。

---

## 二、五类"越界内容"一律拦截

| # | 越界类型 | 典型话术 | 处置 |
|---|---|---|---|
| 1 | **过程自述** | "我撤回上一条""我更正我此前的判断""我重写这段" | **只保留更正后的结论**，撤回动作不写、不叙述 |
| 2 | **自我复盘** | "我这轮犯了 3 次错""我的检出率依赖他人""我这条护栏是第 2 次修订" | 写进项目工作笔记 `notes/<member>.md`，**不进回传** |
| 3 | **自创规则** | "建议新增一条纪律""我给规则加了护栏""建议把这条入 gate" | 成员**只能报现象**（"此处出现过一次 X"）；规则由团长在**阶段收口时统一裁决**，成员不得自行增删规则集 |
| 4 | **对冲式自评** | "置信度中高，但仍存在一定不确定性""总体可控" | 只写**置信度等级**＋**一句**不确定性来源，不写形容词堆叠 |
| 5 | **决策上交** | "请团长裁决""两种方案请领导定" | 先自答三问：涉及对客承诺？金额？红线/法律？**全是"否"→ 自己定并给理由**；有一个"是"→ 才上交，且必须给「选项＋建议＋影响」三要素 |

> **成员最容易滑进去的是第 1 和第 3 类**：因为"承认错误"和"提出规则"在直觉上都像负责。**但对下游有用的只有更正后的结论。**

---

## 三、翻转上限：同一结论最多翻一次

- **第一次翻转**：说明理由（新事实/新解读）即可。
- **第二次翻转**：必须附**新证据**（新的文件、新的数据、对方原文）。**无新证据不受理**，沿用上一版并记「已否决·无新证据」。
- **区分"改结论"与"改措辞"**：措辞修订不产生新版本号，也不触发下游重跑；结论翻转才产生 `v<N+1>`。

> 一天内同一结论翻三次以上，通常不是"越查越准"，而是**一开始就没定判断标准**。此时应停下补标准，而不是继续改结论。

---

## 四、往返预算

| 对象 | 预算 | 超了怎么办 |
|---|---|---|
| 同一议题（一个结论/一处措辞） | **≤ 2 轮**（提出 → 修订） | 第 3 轮由团长直接裁决，或标「待确认」结案，不再往返 |
| 团长对同一成员发消息（含催办） | **≤ 3 次 / 阶段** | 说明任务边界没划清——**重写交接物，而不是继续追问** |
| 一个阶段内的并行成员 | 攒**一批**再组装交接物 | 不"来一条转一条"，否则下游按半成品开工，必然返工 |

---

## 五、团长的转发纪律

1. **不转原话，转三件套**：`结论标签 + 影响面（影响哪些已确认结论/哪些页）+ 需要下游做什么`。
2. **一条消息只推进一件事**；同一成员的多项修改**合并成一条**发出。
3. **不做传声筒**：成员 A 说 B 有错，团长先自行判断，只把**判断结果**给 B，不转述"谁说了你什么"。
4. **不点评成员表现**，只判交付是否达标（四维度：完整性/可追溯/假设标注/上游一致）。
5. **并行阶段的收口**：先收齐、再互相印证、再组装；**禁止把半成品下发给下游换速度**。

---

## 六、停手信号（看到即收束）

出现下列任一表述，团长**不再探讨、不再转发**，回一句固定句式收束：

> 「收到，**结论留下，过程不用写**。回到交付物：<具体缺哪一项>。」

- 「我撤回 / 我更正 / 我重写」
- 「我自报一处缺陷 / 我发现自己矛盾」
- 「我给规则加个护栏 / 建议新增第 N 条 / 建议把这条入 gate」
- 「请团长裁决」（且经三问判断属成员职责内）

**为什么必须硬收**：这类内容读起来"很有洞察"，于是很容易被当作交付继续往下传——**而它每转一次，所有下游都要重新读一遍，却不产生任何可交付物。**

---

## 七、复盘的去向（三处，都不进交接链）

| 内容 | 去哪 | 谁写 |
|---|---|---|
| 过程性洞察、本轮推断、待决分支 | `<project>/notes/<member>.md`（工作笔记，§2.4） | 成员自己 |
| 跨项目可复用教训 | 阶段收口时团长统一提交 → `references/lesson-index.md`（须含**真实案例 + 失效边界**） | 团长 |
| 本轮交付的成本与问题 | 最终报告「成本自检」一行（内容修订 N 次 / 渲染 M 次 / 核验 K 页） | 团长 |

> **复盘不是交付物。** 复盘写在工作笔记与经验索引里，交接链里只走结论。

---

## 八、自检清单（成员回传前照此过一遍）

- [ ] **任务三要素是否已明确**（谁写什么文件 / 发给谁看 / 要达到什么目的，见 `references/task-brief-spec.md`）？缺失 → **拒收并向团长索要**，不计修订轮次；有 → 产出是否对齐三要素（交付物形态 / 受众口吻 / 目的判据）？
- [ ] 结论 ≤5 条、总长 ≤800 字？
- [ ] 每条结论都有出处？
- [ ] 有没有写"我撤回/我自报/我建议加规则"？（有 → 删掉，只留结论）
- [ ] 待确认项是不是"卡住结论的那一个"，而不是泛泛开放题？
- [ ] 要团长裁决的事，三问（承诺/金额/红线）是否真的命中？
- [ ] 与上一版相比，翻的是**结论**还是**措辞**？（措辞不占版本号）

## 九、成员失败与超时的处置（2026-10-26 补）

当日实况：**7 个成员在同一分钟内报同一错误码**（`400 PacRpcClient request timed out after 5000ms`），另 2 个 `aborted`。这是**平台侧故障，不是成员产出问题**；但当时没有处置协议，只能临场判断。

| 现象 | 判定 | 动作 |
|---|---|---|
| **多个成员同一分钟内报同一错误码** | 平台故障 | **停止派发**、不再重试；已落盘产物按"最后一份完整文件"采信，版本号冻结；向用户说明"团队已停，交付不依赖其后续" |
| 单个成员 `aborted`（长任务） | 任务被杀 | 先查产物完整性（行数是否异常、结尾是否截断）：**完整**→采信并标注「产物可能未含最后一步」；**不完整**→重派一次，仍失败则**降级为团长自办**并记录 |
| 成员报"已完成"但没给产物路径 | 视为未交付 | 一律不采信，要求给磁盘路径；给不出 → 判未完成 |

> **铁律：「成员说完了」不等于「东西在那儿」。** 以磁盘为准，不以消息为准。当日两次"已完成"实际是半成品（缺章节 / 文件被占用未替换），都是靠打开文件才发现的。

## 十、成员启用门槛（lean team · 2026-10-26 补）

当日 8 个成员全上，其中 ind / pol / cus / pro / arc 的边际贡献很低（多为"确认没有新信息"），却各自消耗长上下文。

| 触发条件 | 启用 |
|---|---|
| 有客户/上游多格式材料要读 | **doc-in（必启）** |
| 涉及对外数字 / 金额 / 预算 | **dat（必启）** |
| 需要面向受众的叙事与页面素材 | **mat（必启）** |
| 外发前 | **ver（必启，不可省）** |
| 出现**具体的**政策适用 / 行业对标 / 竞品 / 客户画像问题 | 才启 ind / pol / cus（按需，一事一启） |
| 需要分层架构或分期路径（方案 / 投标类） | 才启 arc |
| 纯写作 / 纯排版 / 单点核验 | **不启其余成员** |

**判据一句话**：*"这次如果没有它，结论会不会变？"* 不会 → 不启。

**并发上限**：同一阶段并行成员 **≤ 3 个**。超过后团长验收成为瓶颈，且成员间通过团长中转的二手信息开始互相污染（当日"唯一/牵头/技术收入"三处反复，皆源于此）。

## 十一、上下文腐化与实例更替（2026-10-26 补）

当日实况：同一成员在同一项目内被反复唤醒十余次后，回传逐渐变成"我撤回上一条""我为自己的规则加护栏"——**不是能力问题，是它的上下文里堆满了历史结论**，每次回答都在和旧自己辩论。

| 触发信号 | 判定 | 动作 |
|---|---|---|
| 同一成员在同一阶段被唤醒 **> 2 次** | 上下文开始腐化 | **换新实例**（fresh spawn），交接物重发（L0+L1），不让它在旧上下文里继续修 |
| 成员开始引用**自己上一版的判断**而非依据 | 自查闭环 | 同上；或直接由团长裁决，停止往返 |
| 成员产出开始出现"此前我说过…但现在…" | 元叙述 | 按 §二 越界内容拦截；只收结论 |

> **重建上下文的成本，低于在腐化上下文里纠错的成本。** 这是与"同项目可复用实例"（团长 §6.3）的例外：复用有收益，但**超过 2 次唤醒就该换人**。

## 十二、交付对账：清单 ≠ 实物（2026-10-26 补）

当日实况：改页单写着"P22 去率先"，而 deck 实测 **P8 标题同样含"率先"**，清单没提。这类差异靠人眼翻页必漏。

- 出件后必须跑 `python scripts/ppt_probe.py <deck.pptx> --find <关键词...>`，把每个改动项的关键词定位到具体页号；
- **命中页 ≠ 清单范围 → 立即回问**：是清单漏了，还是该页本就不该改；
- 交付说明里附一行对账结果（如「商电式→P27、Index's→P9、率先→P8/P22/P25」），让用户一眼看出范围是否完整。
