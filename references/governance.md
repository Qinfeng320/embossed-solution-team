## 一、核心原则

- `references/` 是**全团唯一真相源**，其描述（红线文本、知识索引条目）会随交接物注入每个成员的上下文，性质等同 MCP 工具描述——一旦被污染会**随上下文级联**到下游所有产出（见《AI Agent》4.4 工具投毒/提示注入）。
- 因此：**任何回写 `references/` 的改动 = 一次 PR**，不得由任一成员在会话中直接改主分支；必须经独立审核、锁版本、可回滚。
- 这与团长 6.3「禁止回写共享」互补：项目专属数据只进项目工作区；本文件管的是**全局 references 自身的演进**。

## 二、PR + 异源互审协议

1. **Proposer 提最小 diff**：在工作分支上提出尽可能小的改动，包含——
   - 新增/修改条目的**证据引用**（原始政策原文、官方链接、客户授权、上游成员结论标签）；
   - **维护链接与索引**（在 knowledge-index 中更新对应条目、在相关索引页登记）；
   - 时间元数据与「待核实/已核验」状态。
   - 不是把一次对话粗暴追加到文件末尾，而是先检索已有知识再增删改对应条目。
2. **异源 Reviewer 独立审核**：Proposer 与 Reviewer **用不同模型家族**（如生成用 Claude、审核用 GPT；或 Proposer 用 DeepSeek、Reviewer 用 Kimi）。不同训练数据与偏好可降低两者在同一处犯同类错误的概率。Reviewer 主要核对**证据与 diff**，不沿 Proposer 结论复述。
   - **回原文铁律（v1.1 新增·PR-001 实测所得）**：凡 diff 中出现「行 X–Y」形式的原文行号/页码引证，Reviewer **必须逐条打开原始证据文件比对该行区间实际内容**，**禁止只比对上游摘要、diff 自述或凭章节标题推定**。PR-001 中 `mat` §9-⑥「演示诚实契约」原引 11781–11804（实为世界模型路线对比表），真实锚点为 10783–10800 <!-- cite-ignore 本行行号系反面教材，非引用主张 -->——该阻断项正是靠回查原文捕获，摘要级复核不可能发现。此类"张冠李戴"判**阻断级**，修复前不得合入。
   - 引证颗粒度要求：能定位到具体断言的，须在区间内再标出**支撑子行**（如"禁 mock（10800）/ 禁连接提示音（10785–10786）"），使后续复核可点验而非整段泛指。
   - **行号机检闸（v1.2 起已实装）**：合入前须跑 `python scripts/verify_citation_lines.py`——按「中文 2-gram + 术语 token」计算引用主题与原文区间的重合度，判 **PASS / WARN(存疑) / ERROR(张冠李戴·阻断)**，退出码 `0/2/1`。使用纪律：
     - **脚本是筛子不是法官**：它只负责把可疑项挑出来，`ERROR` 与 `WARN` 一律仍须人工回原文定夺，不得据脚本结论直接改文档。PR-002 实测 8 条 ERROR 经回查**全部为伪阳性**，若盲从脚本会误改 8 处正确引证。
     - **阈值须由 `--calibrate` 依产线分布标定**，禁止拍脑袋设定（同 §6.5 熔断阈值纪律）。
     - **改动脚本后必须先跑 `--self-test`**（内置解析层 5 例 + 判别层 6 例，含 B-1 正反锚点）；自检不过则本轮脚本结论一律不可采信。
     - 教学性反例引用（刻意引错误锚点作反面教材）在行内加 `<!-- cite-ignore -->` 豁免，避免闸门反噬正确内容。
   - 配套 `scripts/verify_citation_lines.py` 做行号—原文重合度自动校验（已建·PR-002），将"回原文铁律"从人工抽查降级为机器闸；合入前必须跑该脚本，ERROR 须回原文定夺、WARN 须人工判读（见 §二.2 机器闸纪律）。
3. **权限强制分工**：
   - Proposer **只能写工作分支**；
   - Reviewer **只读**证据与 diff，提交审核结果；
   - 只有**合入流程**可以更新主分支与派生索引。
4. **迭代至收敛**：Reviewer 不通过时返回**指向具体证据与行号**的可执行意见（非模糊"还需改进"）；Proposer 修改后 Reviewer 回到原始证据复核；明确批准方可合入。
5. **封顶转人工**：设最大迭代轮次或成本预算；超限仍未收敛转人工审核，不默认放行。

#### 知识更新三原则（呼应《AI Agent》3.3.3.2）
增量 PR + 异源互审之外，每次整理/修订须落实三条，避免"只在摘要间改写导致早期误读代代传"：
1. **去重、去旧与合并**：语义重复、已被取代、过度碎片化或仅表述差异的条目删除/归并/重写；重建文件间链接、入口页与索引页，必要时拆分过大、合并过小文件。
2. **回到原始数据核查**：不得只在已有摘要之间相互改写（早期遗漏/误读会一代代传下去）；整理 Agent 须逐段对照原始对话、execution trajectory、业务文档与工具输出，检查旧摘要是否遗漏关键事实、丢失否定词或时间条件、把推测错当事实。
3. **冲突解决与场景限定（qualification）**：互相矛盾的说法**不得简单"保留最新一条"或强行收敛成一个确定结论**；应追溯各自原始信息源，若分别在不同时间/对象/地域/任务/前置条件下成立，则把各自适用场景明确写入知识；证据仍不足时**保留冲突与待确认状态**。这与 ver-agent「待确认」纪律一致——不确定的结论宁可标待确认，不可编造确定结论。

### 二'、团队自述文档同步纪律（PR-029 新增 · 2026-11-17）

`references/team-overview.md` 是团队对外自述文档（运作机制详解）的**唯一维护版**（Markdown，开源文档定位）。任何改动**机制、角色、规则、模型分派、流程闸门**的变更合入后，执行三条：

1. **强制同步检查**：Proposer 合入前必须过一遍「本改动会不会改变 team-overview.md 已描述的内容」，PR 记录中**必须写明**「文档同步：已更新 §X」或「文档同步：无需更新（原因）」——缺此项的 PR 视为流程不完整；
2. **版本联动**：每次同步更新文档头部的「文档版本」「对应团队包版本」「最后同步」三个标记，与包版本号保持联动；
3. **Word 不回写**：Word 正式件是按需导出的一次性交付物（经 docx 渲染管线从文档树导出），导出后不回写维护版，也不作为同步对象；对外需要正式件时重新导出。

> **载体分工（PR-035 新增）**：`team-overview.md` 是**标准说明**——描述团队当前的标准机制与现状，随机制调整直接修订正文使所述标准为现行；它**不是更新日志**，不得在其中累积逐次变更流水、版本号演进时间线或「发布记录」表。逐次变更的问题、根因、改法、验证与日期由**变更记录（PR）与发布公告**承载。Word 正式件是标准说明某一时刻的导出快照，不回写维护版、不入专家包。三者职责分离，不得混写。

> 判定口诀：**改动进包，文档跟上**——只要改的东西在 team-overview.md 里有对应描述（角色职责、协作流程、质量指标、模型分派、变更与风险、持续改进、复用指引），就必须同步；纯脚本内部实现、不影响对外机制描述的改动可标「无需更新」并写明原因。

## 三、三分层（原始证据 / 知识 / 服务）

```
原始证据层  raw/      # 只增不改：客户原始材料、政策原文快照、上游成员产出轨迹
知识层      references/ # 可持续修订：redlines / knowledge-index 等 Markdown 真相源
服务层      .index/     # 派生索引（分块/摘要/向量），从已合入的知识层重建，可丢弃重建
```

- Git 中已审核的 `references/` 才是**真相源**；服务层索引是派生物，合入后增量重建。
- 每条知识须能回答「从哪条证据而来、谁在何时批准」（PR 记录证据标识、知识库版本、审核意见、最终决定）。

## 四、信任与版本纪律

- **锁版本、拒静默更新**：`references/` 描述当作**不可信输入审计**；任何外部引用（政策库、案例库）锁版本，升级时重新审查，不在会话中静默刷新。
- **可回滚**：所有改动经 Git 版本控制，支持差异审查、责任追溯、一键回滚。
- **评测系统自检**：当 Reviewer 认为某条知识/红线"过时或不适用"时，先质疑**标准本身**是否该更新（呼应《AI Agent》6.9「看到分数下降先检查评测系统」），而非默认判上游成员违规；标准修订须走本协议的 PR 流程。

### 深挖回灌补充（v1.1·来源 pdf-chapter-deep-mining.md §5·生效 2026-08-08·状态：现行有效·经 PR-001 异源互审）
- **信任边界下移到数据层（§5-③，行 6893–6927）**：权限检查与被约束代码同信任域即失效，须由行级安全 + access context 在稳定层强制；合规红线写提示词/规范文档 = 每次生成可被重写，应落不可绕过的模板与校验脚本——呼应本文件"references 当不可信输入审计"纪律，红线/约束须以脚本/模板承载而非仅文档。
- **服务端/独立数据源真值（§5-①，行 6362–6428）**：事实核验须查库 + 独立数据源，模型自报值只做比对与 log_mismatch，绝不参与裁决；"独立性不仅指独立模型更指独立数据源"。
- **语义解析而非关键字黑名单（§5-②，行 6243–6250）**：约束有效性须语义层判定（"保证就业率"改"就业无忧"即绕过黑名单）；"约束=理解而非匹配"。
- **持久记忆第四要素（§5-④，行 6206–6224）**：写入长期记忆须经与外部内容同等信任审查，否则跨会话潜伏放大；knowledge-index/案例库入库须过"独立数据源核验"闸。
- **产品/训练双轨收录（§5-⑥，行 5995–5997）**：交付稿可留「待确认」占位，但沉淀进 references 必须拒收占位与未核验原文——本文件 PR 协议对"入库"环节强制此双标。

### 四' 共享空间防静默篡改（MAST ③·P0-④·对齐《AI Agent》Ch.10.5.1）

§四 已用「派新即关旧 + 磁盘唯一事实底座」防 MAST ①并发冲突（逻辑层）。本节补 MAST ③**物理层**防护——即便无并发，磁盘内容被静默覆盖/篡改也须可发现：

## 六、实测反馈回流通道（测试反哺方法）

本文件前几节管的是 `references/` 的演进纪律；本节补上**测试方法学漏洞如何回流进包**的通道。一次济南专班真实复测暴露了需求：复测中发现的交付文件核验假阴性（赛曙漏判）、xlsx 实体漏解码、版本漂移漏检等，当时只写进了项目报告与记忆，未折回可复用包，导致下次跑同类核验仍会重蹈。

回流协议（与 PR 纪律同源，但对象含 `agents/` 与 `scripts/`）：
1. **存证据**：实测发现的每个方法学漏洞，原始证据（复测报告、复现命令、前后对比）存入 `raw/` 原始证据层，不丢。
2. **Proposer 提最小 diff**：将教训写成可复用规则——如 ver-agent 的 M1–M4 铁律、input-spec 的实体解码/残留扫描规矩、新增 `scripts/verify_text_count.py`；diff 须含「触发场景 + 错误后果 + 标准做法 + 关联 PDF 范式（若有）」。
3. **异源 Reviewer 审核**：由不同模型家族的 Reviewer 核对证据与 diff，重点看「是否真能防住该类误判、是否与其他成员规矩冲突」。
4. **合入与版本**：agents/references/scripts 改动合入即 bump 对应版本、写 change_log；`references/` 改动仍走本文第一节核心原则（锁版本、可回滚）。
5. **验证落入**：合入后用 Grep 全包核验关键词（如 `html.unescape` / `全 XML` / `版本漂移`）已存在，并 Read 确认结构完整、六红线/预算闸未破坏。

> 失效内容版本化下线（呼应《AI Agent》3.3.3.1）：每条知识/产物须附**版本号 + 生效/失效时间**元数据，在检索/核验阶段过滤已失效内容；同名不同版文件须显式标版本，过期/被取代版本不得与现行版本一起进入交付集（直接对应 ver M4 的「版本漂移 / 失效未下线」核查）。

**经验写回触发条件（PR-011 新增 · 与 `references/lesson-index.md` 对应）**：满足任一即须写回——① 任务完成且产生可复用模式；② 发现新平台/工具链坑点；③ 发现路由缺口（`references/routing-config.json` 未覆盖的意图）；④ 有价值失败（失败原因可复用）；⑤ 维护/清理中发现规范漏洞。写回条目入 `references/lesson-index.md`，已固化为规则/脚本的须注明固化位置；消费侧纪律见 team-lead §6.4。

### 六' 进化闭环 meta 化（P2-⑨·对齐《AI Agent》Ch.8.2「从更新产物到更新更新方法」）

本文件 §六 管"实测漏洞如何回流"。本节把回流升级为 **meta 层**——不仅沉淀具体教训，更让 SOP/references 本身被运行经验反哺：
- **信号识别**：`scripts/evolution_meta.py` 读 run-log，识别三类可沉淀信号——复现失败类别（同 root_cause ≥2 次）、反复知识缺口、多次被采纳的变更模式。
- **提案而非自动合入**：脚本只生成 **governance PR 就绪的 diff 提案**（markdown），交异源 Reviewer 审核；严守「锁版本、拒静默更新」——本脚本不写主分支。
- **与睡眠学习衔接**：提案触发即纳入团长 §6.5 定期整理例程，走本文 PR 协议合入；合入后 bump 版本、写 change_log。

## 七、理论依据：四载体模型与三路径学习（呼应《AI Agent》第 1 / 7 / 8 章）

本治理机制不是孤立约定，而是书中两条主线在文档团队的落地（详见 `references/design-philosophy.md` §13、§16）：

- **三路径学习（Ch.1.1 图 1-1）**：Agent 行为改变发生在三处——任务内适应（当前上下文）/ 外部制品更新（知识·指令·程序）/ 参数更新（训练）。本文件所管的 `references/` 回写 ＝ **外部制品更新载体**：知识（本库）、指令（agent `.md`）、程序（`scripts/`）三类制品跨任务持久、可审计，对应三路径中的"外部制品"一支。
- **四载体模型（Ch.7.13 末段 ＋ Ch.8 图 8-3）**：稳健系统组合使用 RAG / ICL / 程序 / 参数 四类载体，按"能力能否被事实、语言规则或程序完整表达"选择更新位置。本团映射：

  | 载体 | 书中定位 | 团队落点 |
  |------|----------|----------|
  | RAG | 事实与证据，可动态更新、可追溯 | `knowledge-index.md` ＋ 本库（PR 更新、锁版本） |
  | ICL | 零参数即时适应 | 团长交接物 ＋ L0/L1/L2 下发 |
  | 程序 | 确定性流程与硬约束 | `scripts/`（check_budget_consistency 等，ver 的"不会说谎"断链器） |
  | 参数 | 高维感知 / 隐式策略 | **当前不用**（本团能力均可被事实/语言/程序表达，按书标准本就应选前三载体） |

- **三层验证 ＋ 持续进化闭环（Ch.8）**：本文件"PR ＋ 异源互审 ＋ 锁版本 ＋ 实测反馈回流 ＋ 失效版本化下线"＝书中"记录轨迹→形成信号→生成候选更新→验证发布→回归灰度回滚"闭环的文本团队实现；"验证器只给评价与证据、修改由独立模块决定"＝ `ver-agent`（裁判）与团长/治理（决策）职责分离。
- **结论**：本团刻意**不微调模型**，而用 `references/`（RAG 式事实库）＋ 交接物（ICL 式适应）＋ `scripts/`（程序式硬约束）承载知识与约束——这是 Ch.7/8 明确推荐的稳健组合，亦是"苦涩的教训"的工程实践（红线/事实由外部制品承载，不靠模型记忆）。
