# 深度追问协议（Grill Protocol）

> **版本元数据**：`version: v1.0` ｜ 生效 2026-11-17 ｜ 状态：现行有效 ｜ 合入 PR：`references/prs/PR-023-grill-protocol.md`
>
> 中央真相源之一。定义**团长对用户**的「深度追问式需求澄清」——什么时候逐支追问、怎么问、问几轮、怎么收束。呼应 G-1 需求确认闸门（团长 §4.0）与 §3.4 用户沟通规范。
>
> **立门起因**：用户（2026-11-17）明确要求把 grill-me 技能的能力并入专家团——"尤其是在跟我交互的过程中要多用"。原 G-1 / §3.4 的「一次问清（合并一轮、不追加）」适合轻量确认，但对**方向级深歧义**收敛太快：分支之间有依赖时，一轮合并不可能问对顺序，用户也答不出还没被拆开的依赖链。本协议补这一层。

---

## 一、适用范围（管谁 · 不管谁）

- **只管团长 ↔ 用户**。成员 ↔ 团长的回传仍走 `references/communication-protocol.md`，两者不混用。
- **只管深歧义**（会改变交付方向、结论、范围、预算、验收标准的歧义）。执行细节、单点确认不走本协议。

### 触发点（出现即进入 grill 模式）

| # | 场景 | 入口 |
|---|---|---|
| 1 | G-1 开工前需求确认 | 团长 §4.0 G-1 ③（默认走本协议） |
| 2 | 重大口径决策点（选题方向 / 受众定位 / 测算基准 / 取舍类决定） | 团长 §6.5「决策呈交」前，先 grill 拆歧义 |
| 3 | 变更影响面有分歧（用户对"改什么、重跑哪段"的边界与团长判断不一致） | 团长 §6.2 第 0 步后 |
| 4 | 用户明示（"grill 我 / 拷问我 / 追问到清楚为止"） | 直接进入，无需判定 |

---

## 二、模式判别（grill 深模式 vs 快速合并模式）

| 判据 | grill 深模式（本协议） | 快速合并模式（§3.4 ② 原规则） |
|---|---|---|
| 歧义性质 | **会改交付方向 / 结论 / 范围 / 数字** | 执行细节、单点确认 |
| 分支依赖 | 分支间有依赖（答 A 才能定 B） | 各项独立 |
| 问法 | **一次一问，等答再进** | 合并一轮，一次 ≤3 问 |
| 轮次 | 预算内多轮（≤8 问 / 会话） | 一轮，不追加 |

**一句话判据**：*"这个问题的答案，会不会决定下一个问题该怎么问？"* 会 → grill；不会 → 合并。

---

## 三、执行规格（怎么问）

1. **先列分支，再开问**：开问前先向用户亮出本次要收敛的 3–6 个**顶层决策分支**（G-1 场景即六类要素：交付物形态 / 受众用途 / 范围重点 / 素材口径 / 约束红线 / 验收标准；其他场景按各自歧义树列）。让用户看到全貌，知道问到哪里了。
2. **依赖顺序**：从**最基础的分支**问起（其他分支常依赖它；G-1 场景通常是交付物形态或受众用途）。一个分支走完才换下一个；分支内的子决策同样按依赖顺序。
3. **一次一问**：每一问固定三件套——
   - **问题**（一句话，选项化问法）；
   - **为什么影响结论**：说明这个答案会改哪一章 / 哪个交付物 / 哪个数字（用户据此判断值不值得纠结）；
   - **2–4 个选项 + 推荐项**：每项一句话后果，用户短语即可作答（如"选 A"）。
4. **等答再进**：用户回答之后才进入下一问。用户答非所问时，先复述收到的答案确认理解，再继续。
5. **能自答先自答**：可从用户原话、`ProjectContext`、已有材料、`references/` 查到的，一律不问（"先自己查，再开口问"）。
6. **逐支收束**：一个分支的答案落定后，一句话复述该分支的结论，再宣告进入下一分支。

## 四、预算与逃生阀（防疲劳 · 硬判据）

| 项 | 值 | 超限动作 |
|---|---|---|
| 单会话提问上限 | **≤ 8 问** | 触顶仍不清 → 剩余歧义汇总成**一张清单**（每项带推荐）一次呈交，用户批量作答 |
| 收束逃生阀 | 用户说「**按推荐执行 / 其余按你建议**」 | **立即收束**，剩余分支全部按推荐值落定，并在 RB 标注「按建议执行 · 可一句话覆盖」 |
| 模式切换 | 用户说「**一次列全 / 列清单**」 | 切批量模式：剩余分支合并列出，用户一次作答 |
| 返问禁令 | 同一分支**同一问**不问第二次 | 用户没答清 → 换个拆法问子决策，不复述原问 |

**终止判据**：所有分支已解决、没有剩余的"看情况"项。收束时用**一段话汇总本次落定的关键决策**（各分支结论 + 哪些按推荐执行），供用户一眼复核——这段汇总是 grill 会话的交付物，写入 RB / 决策记录。

---

## 五、与既有机制的边界（不重复定义）

- **G-1 六要素**：是分支框架，本协议是问法；问完的产出仍是 RB（G-1 ④），不另立产物。
- **§3.4 ② 一次问清**：保留为快速合并模式；深歧义改走本协议（§3.4 已改写为双模式）。
- **§6.5 决策呈交三要素（选项 / 建议 / 影响）**：与本协议第 3 条「每问三件套」同构——grill 是把决策呈交**逐支串行化**，不是另起炉灶。
- **communication-protocol.md**：管团长 ↔ 成员；本协议管团长 ↔ 用户，双向不越界。
- **grill-with-docs 变体不引入**：本协议即"纯对话拷问"；与项目工作区知识对齐的变体（拷问时实时对照知识库术语）由团长自行结合 `ProjectContext` 完成，不单独立文。

## 六、团长自检清单（grill 前后照此过一遍）

- [ ] 开问前列了 3–6 个顶层分支，并让用户看到了分支全貌？
- [ ] 从最基础的分支问起，而不是从最容易的问起？
- [ ] 每一问都带了「为什么影响结论 + 选项 + 推荐」三件套？
- [ ] 一次只问了一个问题，且等到了回答才进下一问？
- [ ] 能自己查到的是不是都先查了、没拿去问用户？
- [ ] 单会话 ≤8 问？触顶时是否改为清单批量呈交？
- [ ] 收束时用一段话汇总了全部关键决策？
- [ ] 汇总结论已写入 RB / 决策记录（含「按建议执行」标注）？
